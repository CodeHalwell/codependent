# v0.10.0 — the hybrid platform lands; the local product ships, the hosted half does not

This release is the hybrid platform programme
([`docs/superpowers/plans/2026-08-16-hybrid-platform-program.md`](../superpowers/plans/2026-08-16-hybrid-platform-program.md),
milestones M0–M9). It is **large** by volume: nine new SQLite migrations, ten new PostgreSQL
migrations, five new crates, two new TypeScript SDKs, a Tauri desktop shell, and a browser client.

The single most useful thing on this page is the distinction between **built** and **reachable**.
A great deal of this programme first landed as finished, tested code that no client could invoke —
a verifier in an unlinked crate, commands with no handler, a query naming a column that has never
existed. Those are fixed; what remains unreachable is listed as unreachable. "The crate exists and
its tests pass" is not the same as "the feature ships", and this document keeps them apart.

Everything in the shipped binaries — daemon, CLI, TUI, secrets, sandbox, federation, marketplace,
desktop, VS Code — is wired and tested. The control plane, the browser client, and the remote
runner are **source-only** in this release: they are not built into any released artifact.

**Read "Explicitly NOT production-ready" before deploying anything.**

---

## Wired end-to-end — you can use these

These have a durable store, a daemon handler, and at least one client that drives them.

### Session Library

Global search across sessions with provenance and deep links, plus the full lifecycle: rename, pin,
unpin, archive, restore, delete (tombstoned, with a 30-day purge), and export. Indexing is
incremental on ledger append and rebuilds deterministically at startup after an interruption.
Search and lifecycle are owner-scoped by the transport-derived principal before the query runs.

**Driven from VS Code only.** The CLI, TUI, and desktop do not expose search or lifecycle in this
release.

### VS Code editor-native actions

Explain selection, Fix selection, Fix diagnostic, Generate tests, and Review current file, on the
editor context menu and the command palette. Each sends the current IDE context, a source identity,
and an idempotency key into an **ordinary daemon run** — there is no extension-side model or tool
loop, so every one of these is attributable and appears in history like any other run.

### Desktop app connects to the real daemon

`apps/desktop` is now a Tauri shell that opens a genuine Unix socket to the daemon and renders real
protocol events. The simulated sessions and the `setTimeout` that used to fabricate a completion are
gone. When the Tauri shell is not present the app reports honest disconnection instead of showing
fake data. Tauri capabilities are locked to `core:default` — no filesystem, shell, or network
access.

### One shared TypeScript daemon client

`@codypendent/protocol` now carries the framing, the client, and the session store, and both VS Code
and the desktop app consume it. The hand-duplicated frame codec in the extension is deleted. (One
duplicate remains — see "known gaps".)

### Durable inbox

Pending human work is persisted per owner with deduplication, cursor paging, and idempotent
acknowledge/dismiss. Entries are produced on the live path for **approval requests, agent questions,
and run terminal states**. Rendered as a VS Code tree view and a desktop panel.

Acknowledging an inbox entry never resolves the underlying approval or question.

### Measured execution observations and usage analytics

Every run records normalized observations — completion, latency, provider, model, tokens, cost —
keyed by logical run and attempt, alongside the existing run-usage columns. Aggregate queries and
bounded JSON/CSV export are wired to the daemon and driven from the desktop dashboard.

Unmeasured values stay `NULL` and render as explicitly unavailable. **They are never converted to
zero.** In particular `cached_tokens` and `reasoning_tokens` are always `NULL`, because the runtime's
`ModelUsage` type has no such fields — the columns are honest placeholders, not measurements.

### Session bundles (daemon-side)

Deterministic, content-addressed, redacted export and import with manifest hashes, hostile-import
handling (hash mismatch, oversized entries, path and symlink escape, duplicate paths, identity
collision), and imports that receive new local IDs plus imported provenance and never restore
credentials or approvals.

**No client can invoke it.** There is no CLI subcommand, no desktop action, and no VS Code command.
The feature is complete and unreachable.

### Automation binding CRUD

Trigger bindings persist with source config and filter, workflow and version, dedup, concurrency,
retry, misfire, budget, and approval mode. Create/update/delete require Controller. Cron expressions
are validated and a next-fire time is previewed at create time.

**Nothing fires them.** See below.

### Secret broker (interface)

Four wire commands — declare, bind, list, revoke — with context-bound leases (300s TTL),
append-only non-secret audit, and no key material crossing the wire: `SecretBind` returns only a
lease id and an expiry.

**The backends behind this interface are not production-grade.** See the third section.

### Marketplace lifecycle (basic)

`codypendent marketplace search | install | update | enable | disable | revoke` work end to end
against a local package store. Revoking a package blocks a later enable.

**This path performs no signature verification and has no trust model.** See the third section.

### First-party workflow template catalogue

Six automation templates ship as built-in manifests — failing-CI repair, dependency update, stale
document refresh, flaky test investigation, repository health report, release preparation — plus
PR review and security scan. They are compiled into the binary and parsed under the built-in
workflow scope with source precedence.

They cannot yet be started by a trigger, because there is no trigger service.

### Cross-repository federation (M6)

All fourteen federation commands are wired end to end and reachable over the wire: establish a
federated identity, get/set publication policy, publish and tombstone graph facts, query the
federated graph, blast radius, migration planning, reviewer suggestion, and the five campaign
commands. Each carries a decided role floor — reads open to any attached role, mutations
Controller-only — and each resolves real ownership before acting, answering one generic
`federation.repository-not-found` / `federation.campaign-not-found` for "no such checkout", "not
yours", and "no identity established" alike.

Publication fails closed: an absent **or unreadable** policy publishes nothing rather than falling
back to a default, withheld facts have their projection row deleted rather than left served, and a
derived classification may only ever raise sensitivity above the operator ceiling.

Nothing crosses a machine boundary in this release — there is no publication transport, so
`remote_receipt` stays NULL until the control plane ships. Facts are projected locally with
`encryption='none'`.

### Marketplace package verification

The daemon-local implementation that skipped verification has been routed through
`crates/marketplace`. Before anything is written, install now:

1. parses with the real `codypendent_sandbox::parse_manifest`, not a hand-rolled `[package]` reader;
2. **requires artifact bytes** — a checksum with nothing to check is not verification;
3. **requires the publisher to already exist, be trusted, and not be revoked.** There is no
   trust-on-first-use: this path never creates a publisher row;
4. verifies checksum and Ed25519 signature via `PackageVerifier` over trusted, non-revoked keys.

`allow_unsigned` is now honoured and means exactly one thing: it waives a *missing* signature. It
never waives a wrong signature, a bad checksum, or an untrusted publisher, and it defaults to
denying. Install and update also refuse to resolve a legacy `signed = 0` version row without it.

Related fidelity fix: `disable` previously wrote `lifecycle='disabled'` while calling the sandbox's
**irreversible** `revoke()`. The database now records `revoked`, which is what actually happened.

## Explicitly NOT production-ready

Each item here is a real defect or a real absence that a deployment would hit. None is theoretical.

### The control plane is not in this release, and could not be used if it were

`.github/workflows/release.yml` builds exactly three binaries: **`codypendent`,
`codypendentd`, and `codypendent-ui-worker-launcher`.** There is no `codypendent-control-plane`
binary in the release archives, no container image, no Helm chart, no Compose file, and no
`docs/self-hosting/` guide anywhere in the repository.

Even from source it is not usable: `POST /v1/auth/login` returns `501 not_implemented` and touches
no store, and no HTTP route can create a user or mint a first refresh token. Because issuing a
pairing challenge requires an authenticated user principal, **a freshly deployed control plane can
never pair a daemon.**

CI has no PostgreSQL service and no `DATABASE_URL`, so the migration test skips itself and every
other control-plane test runs against an in-memory store. **All ten PostgreSQL migrations and the
entire PostgreSQL store are unexercised by CI.**

What *was* fixed this cycle, so nobody re-litigates it: the unauthenticated login endpoint that
minted credentials for any caller is closed (the request/response types are deleted, so there is no
type through which a token could be returned); the hardcoded default JWT signing secret is gone and
`impl Default` was removed so no fallback exists anywhere in the crate; daemon JWTs are now
validated against the `daemons` row rather than trusted from their own claims, so a revoked daemon
loses authority immediately; `repository_id` from a sync body is authorized before any write; the
publication ceiling is a three-way intersection; WebSocket subscriptions re-check authorization per
delivery instead of once at upgrade, and no longer accept a bearer token in the query string; a
path-traversal in presigned object keys (`../other-org/...`) is refused; and the audit hash chain is
serialized per organization — it also previously hashed timestamps at nanosecond precision while
PostgreSQL stores microseconds, so *every* chain verification would have failed regardless.

**Operational note if you ever do deploy it:** `JWT_SECRET` is now a hard startup requirement. The
service refuses to boot without one, rejects secrets shorter than 32 bytes, and rejects known
placeholder values. Nothing in this repository sets it — no manifest, no Compose file, no CI job —
so a deployment pipeline needs that provisioned before the process will start. That is deliberate.

Do not deploy this. Do not describe it to anyone as available.

### Secret backends: only `environment` resolves material

The broker, the lease model, and the audit trail are sound, and the crypto is now real — but three
of the five backends deliberately refuse rather than pretend.

- The **managed** backend now performs genuine envelope encryption: ChaCha20-Poly1305, a fresh
  32-byte DEK per record, a fresh 96-bit nonce on each of the two layers, and the locator bound as
  associated data. The previous XOR-against-a-repeating-pad is gone.
- The hardcoded `[0x42; 32]` / `[0x24; 32]` keys are gone and **cannot be reintroduced**: the
  constructors reject any key that is a single repeated byte, and an unconfigured backend refuses
  to provision rather than encrypting under a placeholder.
- **Vault** and **keychain** no longer hold plaintext in a process-lifetime map — the maps are
  deleted outright, so there is nowhere for a plaintext value to live. Both refuse with
  `secrets.backend-not-configured`; keychain derives platform support from `cfg!(target_os)`
  rather than a caller-supplied boolean.
- **Workload identity** moved from a length-extension-malleable bare `SHA-256(seed || msg)` to
  HMAC-SHA256, with the seed in a redacting, zeroizing newtype.

`ManagedBackend` has no persistence and no KMS: the KEK lives in process memory beside the
ciphertext, and there is no daemon-facing path to `provision()` yet. In practice **`environment` is
the only backend that returns material in this release** — the others refuse honestly instead of
silently answering "not found".

### Automation persists bindings and never fires them

There is no scheduler tick, no due-row claim, and no lease acquisition — the cron library is used
only to validate an expression at create time, and the computed `next_fire_at` is never read back.
There is no production webhook sink, so a verified GitHub delivery reaches no workflow. The
receipts, attempts, and leases tables that carry the at-least-once guarantee have **no writer at
all**.

A binding you create in this release will sit in the database doing nothing. It will not fire late;
it will not fire at all.

### Budget alerts cannot fire

The threshold evaluator, the alert type, the dedup key, and the inbox entry kind all exist and none
is connected. There is no command, CLI, or UI that can create a budget, and the evaluator has no
production caller. You will never receive a budget warning.

### Route promotion: canary evidence is now measured, not asserted

`PromotionAction::ObserveCanary` no longer carries a `metrics` payload at all, and the five CLI
flags that let an operator type the numbers are gone. There is no field left through which a caller
can assert a sample count. The daemon derives the evidence itself from `execution_observations` —
real per-run rows — comparing the candidate model against everything else running concurrently in
the same slice, so `MIN_CANARY_SAMPLES = 100` is satisfiable only by 100 genuine terminal runs.

It fails closed on every gap, with distinct non-retryable codes: an artifact kind whose runs cannot
be attributed, no measured candidate executions, no concurrent baseline, or latency unmeasured on
either side. An absent latency is never treated as 0 ms.

**Only `model-profile` candidates can be promoted.** Skill, prompt, router, workflow and retrieval
candidates refuse with `promotion.canary-unattributable-artifact`, because nothing in the recorded
executions ties a run to them — measuring ambient traffic and calling it evidence would be worse
than refusing.

### Native notifications do not exist

The inbox renders inside VS Code and inside the desktop app. Neither raises an OS notification —
the desktop build has no notification plugin and no capability grant for one. If the window is not
in front of you, nothing will tell you a run is waiting.

### Council member sessions still pollute history

Sessions created by the internal council are not marked internal and are never archived, so they
appear in ordinary session listings. The equivalent workflow path is correct; only the council path
is missing.

### Known gaps that are not defects, but will surprise you

- **Session bundles have no client.** Export/import work; nothing calls them.
- **The Remote UI renderer was extracted and is shared by one host.** The desktop uses the shared
  package; VS Code still carries its own diverging copy.
- **VS Code still hand-mirrors the wire types.** A generated package and an 809-line handwritten
  mirror are both imported by the same files.
- **No golden vectors exist for the control-plane protocol, the runner protocol, or federation.**
  The compatibility guarantee those milestones describe has nothing behind it yet.
- **`cached_tokens` / `reasoning_tokens` are always `NULL`** — see above.
- **A sandbox profile with a non-empty network allowlist is still refused outright**, and the
  sandbox always unshares the network. This is deliberate fail-closed behavior; two doc comments in
  that file still describe a conditional that does not exist.

## Migrations

Nine new SQLite migrations (`0041`–`0049`) and ten new PostgreSQL migrations (`0001`–`0010` under
`crates/control-plane/migrations/`). Root migrations remain append-only and checksum-gated.

Note the two sequences reuse the same low numbers deliberately — read the path, not the number.

Five of the PostgreSQL migrations (`0006`–`0010`) create tables that **no code in the repository
reads or writes.** They are applied at startup by a service that is not in the release. They are
forward-looking schema, not a working subsystem.

## Upgrading

```sh
codypendent update v0.10.0
```

or

```sh
curl -fsSL https://raw.githubusercontent.com/CodeHalwell/codypendent/main/install.sh | bash -s -- v0.10.0
```

`install.sh` requires the GitHub CLI (`gh`) on `PATH`.

Local-first operation is unchanged and remains the only supported mode: the daemon starts and runs
with no control-plane configuration and no network, exactly as in v0.9.0. Nothing in this release
introduces a hosted dependency, an inbound port on your workstation, or any automatic sharing of
source, transcripts, artifacts, memories, or credentials.

code — it was finished, tested code with no caller.** Three crates and 581 lines of SQL passed every
gate while being unreachable. Before ticking a box, grep for the symbol; then check that something
calls it.
