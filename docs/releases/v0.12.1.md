# v0.12.1

A patch release: three deferred items from v0.12.0, plus the fixes that came out
of adversarially verifying them.

## Memory history repair (migration 0051)

v0.12.0 fixed `MemoryStore::correct`, which had been stamping corrections with
`valid_from = edit:<uuid>` instead of claiming a sequence revision. Revisions are
compared as TEXT, and `'e' < 's'`, so every correction sorted *before* every real
`seq:` revision. That fix governs new corrections only; a database that ran the
old code still holds the broken revisions. Migration `0051` repairs them.

The repair is deliberately narrow, and the boundary is the interesting part. A
token is rewritten only when no orderable revision exists anywhere downstream of
it — for those, appending above the store's current maximum cannot invert an
interval. A token that *does* have an orderable revision below it (corrected
under ≤ v0.11, then corrected again under v0.12.0) has no representable slot: the
sequence space is dense, because every claim takes `MAX + 1`, so no integer
exists between such a token's floor and its ceiling. Rewriting those anyway
pushes the intermediate row's `valid_from` past its own `valid_until`, which
hides that row at every revision and makes two contradicting versions of the same
fact visible at once.

**Known residual.** Those mixed-era chains are left exactly as the old code wrote
them, so their pre-existing mis-ranking survives: a query at the original fact's
revision still answers with the correction that replaced it. This is not caught
by `MemoryError::NonOrderableRevision` — that guard is on the `as_of` *argument*,
not on stored rows, so an `edit:` revision in the table mis-compares silently.
0051 neither fixes nor worsens this, and it is pinned by a test so it cannot
drift unnoticed. Repairing it properly needs a wider revision space than a patch
release should introduce.

## The remaining unbounded render loops

v0.12.0 bounded three panes. An audit of all 42 `.skip(` sites in `render.rs`
found eight more render loops that formatted every row in the model and let the
`Paragraph` clip the overflow: `render_provider_picker`, `render_theme_picker`,
`render_api_keys`, `render_add_model_pick`, `render_unsloth_repos`,
`render_unsloth_quants`, `render_backtrack`, and `render_context_pane` — the last
of which had no window at all. All eight are now bounded to the pane's row
capacity.

Measured on the worst case (the provider picker, 3-line rows), fixed-iteration
user-CPU harness, 4000 rows × 300 draws: **15.4 ms → 0.70 ms of user CPU per
frame, 22×**. The already-bounded `issues` pane was used as a control and did
not move.

The eight hit-registration loops that follow a `.skip(first)` were already
bounded — each breaks when `visible_row_hit` returns `None` — so there were no
phantom click targets to remove.

## Desktop pause/resume and the pending-prompt queue

The desktop app gains the run controls and the prompt queue the TUI already had:
pause, resume, and a queue that accepts prompts while a run is in flight and
drains them when it finishes.

## Desktop: streaming cost and navigation flow

Two problems reported from actually using the app rather than testing it.

**It was slow while streaming, and got slower the longer a session ran.** Every
token replaced the transcript array, so React reconciled the entire history once
per token — measured at 4.29 ms per token against a 400-item transcript, linear
in the history. Worse, `Transcript`'s scroll effect depended on that array, so
each token started a `scrollIntoView({ behavior: "smooth" })` that the next token
abandoned: thousands of layout-forcing animations per reply, none of which ever
completed.

Transcript rows are now memoized behind a stable-callback boundary, `Navigation`
(6 groups, 22 destinations) is memoized too, row styles are module constants
rather than per-frame allocations, and the scroll is an rAF-coalesced `scrollTop`
that only fires when the reader is actually at the bottom — which also fixes
being yanked back down whenever you scrolled up to read something.

Full-app cost per streamed token, same harness before and after:

| transcript history | before | after |
| --- | --- | --- |
| 50 items | 2.49 ms | 1.47 ms |
| 400 items | 6.06 ms | 2.54 ms |

That measurement runs under jsdom, where `scrollIntoView` is a no-op, so it
excludes the abandoned-animation cost entirely — the real-world improvement is
larger than the table shows. `npm run perf` in `apps/desktop` runs this harness;
it is deliberately outside the gate, because a timing assertion in CI is a flake
generator.

**Navigation was a wall with no way out.** 22 destinations were listed flat in
the sidebar, and Escape did nothing unless the palette was open, so every
secondary view had to be left by aiming at the sidebar again. Sidebar groups are
now collapsible and open on the session surfaces, with the group holding the
current view pinned open; Escape closes the palette if it is open and otherwise
walks back through view history, falling back to the session rather than to
nothing. Every surface remains reachable — the palette still reads the whole
`NAV_GROUPS` table and `NAV_COVERS_EVERY_VIEW` still proves that table covers the
`DesktopView` union.

## Fixes from adversarial verification

Two of the twelve claims made by the implementation agents were refuted on
review, and both refutations were correct:

- **The migration inverted mixed-era chains.** The first version assigned every
  `edit:` token `MAX + k`, which produced exactly the inverted interval described
  above. Reproduced against the real SQL, then fixed by excluding tokens with an
  orderable ceiling. Both the repaired and the declined cases are now covered by
  tests that fail if the exclusion is removed.
- **The desktop's sibling-run guard was unproven and incomplete.** It covered
  `RunStateChanged` only, and its test passed identically with the guard deleted.
  A session can hold several concurrent runs, so a sibling's `RunCompleted` still
  wiped the watched run off the surface entirely, and a sibling's `RunStarted`
  still hijacked it. All three events now discriminate on `run_id`, and a run
  event arriving with nothing on screen is adopted rather than half-applied —
  previously that left `isRunning` true against a null `activeRunId`, a surface
  claiming a live run it could neither pause nor cancel. Four tests cover this,
  each verified to fail when its guard is reverted.
