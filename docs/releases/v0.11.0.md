# v0.11.0 — automation fires; the surfaces ship; the bindings still have no author

v0.10.0 ended with one lesson: *the dominant failure mode was not missing code — it was
finished, tested code with no caller.* This release is the follow-up wave that goes after that
class directly. It closed the largest instances of it and it found new ones, and this document
keeps them apart in the same three sections v0.10.0 used.

The headline is real: **automation now fires.** The scheduler is constructed in
`run_daemon`, its tick loop is spawned, and `automation_receipts`, `automation_attempts` and
`automation_leases` have INSERTs for the first time in their existence.

The headline caveat is equally real and is stated up front rather than buried: **no shipped
binary can create an automation binding.** `CommandBody::ManageAutomationBinding` exists in the
protocol, has a decided role floor, a real `named_resources()` arm and a wired daemon handler —
and outside `crates/daemon/tests/` and `crates/protocol/`, nothing in the repository ever
constructs it. There is no CLI subcommand, no TUI palette entry, no VS Code command and no
desktop action. The engine is reachable; its input is not. Read "Explicitly NOT
production-ready" before you plan around automation.

No new migrations. The highest root migration is still `0049`.

---

## Wired end-to-end — you can use these

These have a durable store, a daemon or daemon-assembly caller, and at least one client or
production path that drives them.

### Automation actually fires

`crates/daemon/src/automation_scheduler.rs` (2,772 lines) is the writer the automation tables
never had, and `crates/codypendentd/src/automation.rs` is the assembly that gives it its two
production callers inside `run_daemon`:

* `start_automation_scheduler` spawns the tick loop (`TICK_INTERVAL = 30s`), so a cron or
  one-time binding whose `next_fire_at` has arrived is claimed, reserved and started;
* `AutomationWebhookSink` is the `WebhookEventSink` the ingestor was built for and never had,
  fanning a verified, deduplicated delivery out to every enabled binding on that endpoint.

The exclusion is durable, not in-process:

1. **A durable lease with a fence.** `automation_leases` is taken with an
   `INSERT … ON CONFLICT (binding_id) DO UPDATE … WHERE expires_at < ? OR holder = ?
   RETURNING fence` (TTL 300s). The migration explicitly forbids reusing the in-process
   `DriveLockRegistry` here — a `HashMap` in one process survives neither a restart nor a
   second daemon instance.
2. **The fence is re-checked INSIDE the claim.** The claim opens `BEGIN IMMEDIATE` and re-reads
   the live fence for this holder first; a higher fence means another instance took the lease
   between the acquire and the transaction, and this tick writes nothing.
3. **A compare-and-swap on the exact `next_fire_at` that was read.** `enabled = 1` and the
   precise `next_fire_at` string are part of the `UPDATE` predicate, never a pre-read.
   `updated_at` is deliberately not touched, because it orders the client's keyset pagination.
4. **`ON CONFLICT (binding_id, dedup_key) DO NOTHING RETURNING id`** on the receipt insert.
   `UNIQUE (binding_id, dedup_key)` is the entire crash-consistency mechanism, so a conflict is
   a normal outcome and never an error; `None` means the occurrence or delivery was already
   reserved.

The scheduler refuses rather than guessing throughout. A refusal leaves the binding row
untouched so a refused occurrence is not silently consumed. A moved or renamed checkout is
detected by re-deriving `RepositoryId` from the path. The daemon will not start the scheduler
at all — with a warning, never fatally — if there is no `WorkflowStarter` (it would claim
occurrences it cannot start and drop the work) or if its own uid is unreadable (ownership could
not then be checked).

The webhook sink is **policy-gated, not implicitly on**: `<data_dir>/webhooks.toml` must set
`automation_dispatch = true`, which is separate from `enabled` (that only opens the listener).
The default is `false`, and enabling the listener alone does not enable dispatch.

**What the scheduler will not do is in the third section.** Several binding shapes are refused
with a dotted code rather than run: see "Automation refuses more binding shapes than it runs".

### `automation_endpoints` now has a writer, so it governs something

Migration 0044 gave every inbound webhook endpoint its own signing-key reference, body ceiling
and replay window, and `SqliteDeliveryStore::resolve_endpoint` read them on every delivery. The
table had exactly one reader and **no INSERT anywhere in the repository**, so `resolve_endpoint`
returned `None` for every request that ever reached the listener and the per-endpoint controls
governed nothing.

`codypendent webhook endpoint add | list | rotate | disable` is that writer
(`crates/cli/src/webhook_endpoints.rs`). It is an offline maintenance command that opens the
migrated database directly — no daemon restart is needed, because `resolve_endpoint` is a
per-request SELECT. Two things it refuses to do:

* **persist key material** — `signing_key_ref` is a public column, so only an `env:NAME`
  reference is stored: the name, never the value;
* **register an unreachable id** — the id is round-tripped through the listener's own
  `parse_endpoint_id` before it is stored, so no row can exist for a path the HTTP surface would
  not route to it.

An unregistered endpoint keeps `UNREGISTERED_BODY_LIMIT_BYTES` (1 MiB), the *tighter* value, so
`add` with no explicit limit changes only who holds the key.

### Session Library search and lifecycle in the TUI and the CLI

Previously VS Code only. Now:

* **TUI** — `/library` in the command palette opens the overlay, with `Alt+P` pin, `Alt+A`
  archive, `Alt+R` rename and `Alt+E` export. The intents are framed as real
  `SearchSessions` / `MutateSessionLifecycle` commands in `crates/cli/src/tui.rs`
  (`SearchSessions` is framed directly by the harness because its reply must be correlated with
  the query).
* **CLI** — `codypendent session search | rename | pin | unpin | archive | restore | delete |
  export`. `delete` takes `--tombstone-only`; the daemon remains the retention authority and may
  refuse a mode rather than weaken retention. Export defaults to Markdown, and
  `--include-artifacts` / `--include-internal` are both off by default because an export widens
  what leaves the daemon.

Everything is scoped daemon-side to the sessions the calling principal owns.

### Session bundles have a client

`codypendent bundle export | import`. This is the "complete and unreachable" item from v0.10.0
closed. Every category is opt-in — with no `--include-*` flag the archive carries only its
manifest — and the collision policy on import is explicit (`reject` / `remap` / `skip`).

### Analytics budgets can be created, and budget alerts fire

Two halves joined. `CommandBody::ManageAnalyticsBudget` has a decided role floor (reads open to
any attached role, `Create`/`Update`/`Delete` Controller-only), `named_resources()` returns a
real `NamedResource::Budget(id)` for the variants that name one, it is listed in the
`every_client_issued_command_has_a_decided_role_floor` guard test with both a read and a
mutating representative, and `codypendent budget` is the client.

The evaluator has a production caller: `crates/daemon/src/ledger.rs` calls
`analytics::evaluate_budgets_in` at a run's terminal write, **inside the same transaction** as
the observation upsert, so the run that crossed the threshold is part of the sum that decides
it. A crossing files a `BudgetWarning` inbox entry deduped on `budget:{id}:{window_start}` —
the exact key `BudgetAlert` carries — so re-evaluating on every later run in the window updates
one row instead of minting a new one.

Two honesty properties worth naming. The entry is filed against the repository of the run whose
measurement crossed the line, never a placeholder; a run with no resolved repository produces no
entry at all rather than a fabricated attribution. And a budget-evaluation failure is logged and
swallowed — it must not fail the run's terminal write, because the run really did finish.

### The desktop app and the VS Code extension are built, packaged and installable

The desktop app's entire Rust side lives in `apps/desktop/src-tauri`, its own workspace root, so
neither `cargo build --workspace` nor `cargo check --workspace` ever compiled it. A new
`desktop-bundle` job does, on two targets, and it is the only thing in the repository that
produces an installable desktop artefact. The VS Code `.vsix` is packaged once (it is
platform-independent) by `vsce package`, which re-runs `vscode:prepublish` so the bundle inside
the `.vsix` is the one the quality job just proved.

`codypendent install desktop` and `codypendent install vscode [--in cursor]` fetch those assets
from the same GitHub release the CLI comes from, via `gh`, exactly as `codypendent update` does.

**On signing, stated plainly because the artefact names depend on it.** There are no Apple
signing or notarization secrets in this repository, so the macOS bundle is **unsigned and not
notarized**. That is why macOS ships a `.tar.gz` of `Codypendent.app` and *not* a `.dmg`: `gh
release download` sets no `com.apple.quarantine` attribute, whereas a browser-downloaded `.dmg`
arrives quarantined with no notarization ticket, and macOS 15 removed the right-click → Open
bypass. Attaching a `.dmg` would ship something that looks installable and is not. A browser
download of the same tarball needs
`xattr -dr com.apple.quarantine /Applications/Codypendent.app` to launch. The signing env is
wired so that adding the secrets later makes Tauri sign with no workflow change, and the job
writes the signing status into the run summary so nobody has to infer it from the absence of a
secret.

Two deliberate narrowings: there is **no Intel-macOS desktop bundle**, so
`codypendent install desktop` refuses on that platform (and says the CLI itself *is* built for
it) rather than installing an Apple-Silicon `.app` that cannot launch; and `--in zed` refuses,
because Zed has its own extension format and no `--install-extension` for a `.vsix`.

The publish job's release-set check is now counted per extension — 4 `.tar.gz`, 1 `.AppImage`,
1 `.vsix` — so a new artefact cannot slip in unnamed and a missing one names its own kind.

### The VS Code protocol mirror is gone

`extensions/vscode/src/protocol/types.ts` — 811 hand-written lines mirroring the wire types
alongside the generated `@codypendent/protocol` package, both imported by the same files — is
deleted. Every daemon wire type in the extension now comes from the generated package.

One locally-declared view remains, `src/remote-ui/wire.ts`, and it is not a second mirror: the
generated `UiWireMessage` nests schema-generated `UiDocument`/`UiPatchBatch`/`UiEvent` trees
while the webview renderer, store and slot registry are typed against `@codypendent/ui`'s
versions of the same trees. The bytes are identical, the type families are not assignable, so
one declaration cannot serve both sides. **Drift is guarded, not trusted:** every field is
checked against the generated type at compile time by
`test/remote-ui-wire-conformance.test.ts` as a partition — each generated field is either
modeled or named in an explicit "not modeled" list — so a field added on the Rust side fails
`npm run typecheck` with the field name in the error. What would let the file go is
`@codypendent/ui` consuming the generated node types instead of declaring its own.

### The control plane consumes its own protocol crate; one audit hash, not two

`crates/control-plane` now depends on `codypendent-control-plane-protocol` and consumes it
across `authz`, `audit`, `store/postgres` and the `sync`/`orgs`/`repos`/`objects` routes.

The audit fix is the concrete payoff. `crates/control-plane/src/audit/mod.rs` owns **no** record
type and **no** hash function of its own — it re-exports the protocol's and adds only the
`bytea`/`uuid` ↔ hex-string adapters the PostgreSQL schema needs. It previously carried a second
`AuditRecord` and a second `compute_record_hash` that hashed `actor_kind` as a raw `&str` where
the protocol hashes its JSON encoding, and hashed a 32-zero-byte genesis where the protocol
hashes `b"GENESIS"`. A chain written by one could not be verified by the other, and nothing in
either crate's tests could notice. There is now exactly one function,
`AuditRecord::compute_hash`, and both stores call it.

### Native OS notifications, for the two things that block a human

v0.10.0's "Native notifications do not exist" is closed on both hosts, and deliberately
narrowly. Exactly two event kinds notify, because exactly two of them stop a run until a person
acts: `ApprovalRequested` and `QuestionAsked`. `RunCompleted`, `ToolStarted`/`ToolCompleted`,
`BudgetWarning`, `ContextUsage`, `PatchProposed` and every variant a newer daemon invents are
information and belong to the transcript and the inbox badge. Over-notifying is treated as a
defect, not as thoroughness: a harness that pops a toast per tool call trains the user to
dismiss toasts, which loses the two that mattered.

Nothing is announced that the daemon has not stated. A replayed range — `history`, or a
`Catchup` — is folded first, so a request whose `ApprovalResolved`/`QuestionResolved` is in the
same range stays silent. A compacted `Snapshot` announces only its `pending_approvals`, the
daemon's own pending set; the projection carries no pending questions, so after a compaction the
client says nothing about questions rather than guessing. One notification per daemon id, ever,
so a reconnect that replays an event does not re-announce it.

The desktop grant is deliberately **not** `notification:default`: it is exactly
`notification:allow-is-permission-granted`, `allow-request-permission` and `allow-notify`, which
withholds the channels, scheduling and cancellation the webview has no use for. No filesystem,
shell or network capability is granted; every other effect still rides the daemon protocol.

### Council member sessions no longer pollute the library

Also from v0.10.0's list. Council child sessions are now created with `internal: true` and
`parent_session_id` set to the session the deliberation was started from, and each is archived
before it is closed — mirroring the workflow path's `archive_internal_sessions`. With
`internal: false` an eight-member two-round council buried the operator's own sessions under
seventeen `Council · …` rows.

The archive is issued *before* `CloseSession` and is best-effort, both on purpose:
`reconcile_once` is retried as a whole, so archiving after a successful close would strand the
row unarchived whenever the close landed and the archive did not; and closure is the
load-bearing operation, so failing cleanup over a hygiene mutation would leak an owned session
that is still open. `internal = true` already keeps the row out of `ListSessions` and the
library's default browse, so a missed archive is cosmetic where a missed close is not.

### The code-graph scanner incident

This one is worth reading in full, because the root cause is a Git behaviour most people do not
know about.

**`git rev-parse --show-toplevel` does not answer "is this directory a repository" when `GIT_DIR`
is set in the environment. It answers with the current directory, whatever that directory is.**
Verified on git 2.55.0, in a `$HOME` holding no `.git` at all:

```text
$ git rev-parse --show-toplevel
fatal: not a git repository (or any of the parent directories): .git
$ GIT_DIR=/some/other/repo/.git git rev-parse --show-toplevel
/Users/<user>
```

So a daemon that inherited `GIT_DIR` — started from a git hook, `git rebase -x`, `git bisect
run`, or any shell where it was exported — made root discovery answer `Some($HOME)` for a
directory that is not a repository, and the scan gate passed. `.gitignore` failed in the same
direction: `git check-ignore` asked in `$HOME` consulted the *other* repository's rules, so
nothing under `Library/` was excluded, because that repository had never heard of it.

The measured consequence on one real user database: **510,904 nodes**, of which **386,572 (76%)
came from one junk "repository" rooted at `$HOME`** — JetBrains' vendored Rust stdlib cache
under `Library/Caches/JetBrains/…/vendor/windows-sys/…` and Cursor's per-edit file history under
`Library/Application Support/Cursor/User/History/…`. A single vendored `windows-sys` Win32
bindings `mod.rs` folded to 10,218 nodes; the next two to 4,959 and 4,947. Every run then spent
**30–60 seconds in `Preparing`** before the model was called.

Three fixes, each addressing a different half of it:

1. **The root question is asked in a clean environment.** The scanner's git invocations strip
   `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`,
   `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CEILING_DIRECTORIES` and
   `GIT_DISCOVERY_ACROSS_FILESYSTEM`. The rest of the codebase already treats these as a hazard
   from the other direction (`is_denied_env` refuses a model-supplied `GIT_DIR`), but it lets git
   inherit the daemon's own environment — correct for a command operating on a *known* checkout
   and wrong for the one command whose whole job is to decide which checkout that is.
2. **A filesystem-shape refusal on top of the answer.** `resolve_scan_root` additionally refuses
   any resolved root that is the user's home directory (compared canonically, since `$HOME` is
   frequently a symlink) or that has fewer than two named path components — an account or
   filesystem root on every layout there is, and no checkout lives at one. The depth rule is what
   covers the roots this process cannot name: `$HOME` comes from the environment, which a daemon
   running as another user or a container with no `HOME` may answer differently or not at all.
   It fails closed — an ambiguous root is refused, never walked.
3. **Two node budgets, because `SCAN_FILE_CAP` counts the wrong thing.** A file's contribution to
   the graph is unbounded, so 2,000 files of generated-bindings shape fit inside the file budget
   and still produce 386,572 nodes. `SCAN_FILE_NODE_CAP = 3,000` skips one file and continues —
   a file worth thousands of symbols is generated code, and folding it buys the model nothing
   while pushing real source out. `SCAN_NODE_BUDGET = 120,000` stops the scan and keeps what it
   accepted. The sizing is arithmetic on the incident's own numbers: subtracting the junk
   repository leaves 124,332 nodes across every real checkout that user had, so the
   per-repository budget is roughly that entire legitimate graph granted to a *single*
   repository. The file cap sits in the measured gap between the two populations — 2.7× above
   this workspace's largest hand-written file (`crates/runtime/src/agent.rs`, 1,123 nodes) and
   1.6× below the smallest generated file that caused the incident.

Plus **cache-tree exclusions** by exact, OS-defined capitalised name (`Library/Caches`,
`Library/Application Support`, `AppData/Local`, and XDG `.cache` needs no entry because it is
dot-prefixed), pruned at the root so everything below goes with it.

The budget preflight costs nothing extra: it *is* the parse the fold already performed purely to
validate, with the node and edge counts kept rather than discarded. Either budget biting sets
`truncated_by_cap`, which suppresses the retire pass — a scan that declined to fold a path has
not established that the path is gone, so it must not delete what a previous complete scan
stored for it. That is the same property the file cap already had.

## Explicitly NOT production-ready

Each item here is a real defect or a real absence that a deployment would hit. None is
theoretical, and every one was checked against the tree as it stands.

### No client can create an automation binding

This is the most important sentence in the release. `CommandBody::ManageAutomationBinding` is
fully correct on the daemon side — decided role floor (reads open to any attached role,
`Create`/`Update`/`Delete` Controller-only), a real `named_resources()` arm, a wired handler,
cron validation and a `next_fire_at` preview at create time, an entry in the
`every_client_issued_command_has_a_decided_role_floor` guard test with both a read and a
mutating representative, and integration coverage in
`crates/daemon/tests/automation_it.rs` and `server_it.rs`.

And a repository-wide search for `ManageAutomationBinding` outside `crates/protocol/` and
`crates/daemon/` finds **nothing**. No CLI subcommand, no TUI palette command, no VS Code
command, no desktop action.

So the practical position in v0.11.0 is: the firing engine is genuinely live and will genuinely
fire a binding — but the only way to get a binding in front of it is to write the row into SQLite
yourself. **Do not plan on scheduled automation in this release.** The scheduler, the lease, the
CAS claim and the receipts are the hard half and they are done; the author surface is the missing
half and it is not.

(By contrast, the webhook side's operator surface *does* exist: `codypendent webhook endpoint`
writes `automation_endpoints`, and `webhooks.toml` — a file the operator writes by hand into the
data directory — opens the listener and, separately, dispatch.)

### Automation refuses more binding shapes than it runs

Everything below is a deliberate refusal with a dotted code, chosen because the alternative is
worse than not firing. None of them is a bug to be worked around; all of them are behaviour to
plan around.

- **`ConcurrencyPolicy::Queue` and `::Replace` refuse** with
  `automation.concurrency-unsupported`. `queue` needs a durable pending-firing queue and
  `replace` needs to cancel the in-flight run through `WorkflowLifecycle`; neither seam is
  wired. Treating them as `allow` would silently double-run an automation whose author asked for
  exactly the opposite. Only `Allow` and `Skip` run.
- **A non-`Inherit` approval mode refuses** with `automation.approval-unenforceable`, and is
  deliberately not given a field to travel in. Nothing downstream can honour a run-level
  approval floor: an agent node never consults `CompiledNode::approval` (only the
  `repository.test` tool node does), there is no run-scoped "require approval for every effect"
  switch anywhere in the runtime, and no path consumes a pre-issued approval receipt. Carrying
  the mode would make `always_require` *look* enforced while agent effects executed unapproved.
- **A tool-call or token budget dimension refuses** with `automation.budget-unenforceable`. Two
  of the four `budget_*` columns are enforceable across the workflow-start seam and two are not:
  the workflow envelope has no tool-call dimension (only a per-role profile slice does, and a
  binding cannot reach one), and tokens are recorded but never charged.
  **Wall-time and cost ceilings do carry** — `StartWorkflowRequest::budget_ceiling` tightens the
  run's *stored* manifest, so the ceiling is charged by `BudgetLimits` for every node and
  survives a restart because the envelope in force is recompiled from that manifest. It may only
  ever tighten: the lower of (declared, imposed) wins per dimension, and a dimension the ceiling
  leaves unset is untouched. A missing ceiling stays `NULL` and is never coerced to `0`, which
  would mean "no budget at all"; a stored non-positive value refuses too.
- **`TriggerFilters` `paths` and `labels` match nothing.** The event normalizer produces no field
  carrying changed paths or labels, so `event_matches_filters` returns `false` outright for any
  binding that sets either. A binding narrowed on `paths` or `labels` **narrows to nothing and
  will never fire.** This is fail-closed on purpose — the alternative is running an automation
  whose author narrowed it and getting the wide behaviour anyway — but it means those two filter
  dimensions are unusable, not merely approximate. `branches`, `actors` and `metadata` do match.
- An unrecognized concurrency or missed-run policy refuses with `automation.unknown-policy`
  rather than guessing, which matters most for a hand-edited row or a downgrade.

### The `cargo nextest` aliases are inert and CI does not use nextest

`.cargo/config.toml` defines `nt` and `ntw`. **cargo-nextest is not installed** — `cargo nextest
--version` reports "no such command" — so both aliases fail until someone runs
`cargo install cargo-nextest --locked`. CI deliberately runs `cargo test`, not `cargo nextest
run`: nextest does not run doctests, and the performance table that once justified the swap
(2.6×–3.5×, with a 2-in-6 flake rate) was attributed to a machine where nextest has never been
installed and was not reproducible. The aliases are a convenience for someone who installs it;
they are not what gates, and they are not a supported path in this release.

### The control plane is still not in this release, and still could not be used if it were

`.github/workflows/release.yml` builds exactly three binaries — `codypendent`, `codypendentd`
and `codypendent-ui-worker-launcher` — plus the desktop bundle and the `.vsix`. There is no
`codypendent-control-plane` binary, no container image, no Helm chart, no Compose file and no
`docs/self-hosting/` guide.

Even from source it is not usable. `POST /v1/auth/login` returns `501 not_implemented` and
touches no store, and **no HTTP route can create a user or mint a first refresh token.** Because
issuing a pairing challenge requires an authenticated user principal, a freshly deployed control
plane can never pair a daemon. CI has no PostgreSQL service and no `DATABASE_URL`, so the
migration test skips itself and every other control-plane test runs against an in-memory store:
**all ten PostgreSQL migrations and the entire PostgreSQL store remain unexercised by CI.**

**`JWT_SECRET` is a hard startup requirement.** The service refuses to boot without one, rejects
secrets shorter than 32 bytes, and rejects known placeholder values. **Nothing in this
repository sets it** — no manifest, no Compose file, no CI job — so a deployment pipeline would
need it provisioned before the process starts. That is deliberate.

Do not deploy this. Do not describe it to anyone as available.

### The remote runner is still source-only

`crates/runner` has no `[[bin]]`, no network client (the only control-plane client is
in-memory), no server-side scheduler and no container image. Its three migrations have no Rust
caller. It now has golden vectors, which stabilises the wire contract and changes nothing about
reachability.

### Secret backends: only `environment` resolves material

Unchanged from v0.10.0 — `crates/secrets` was not touched in this release. The broker, the lease
model (300s TTL), the append-only non-secret audit and the crypto are sound: the managed backend
performs genuine envelope encryption (ChaCha20-Poly1305, fresh 32-byte DEK per record, fresh
96-bit nonce on each layer, locator bound as associated data), the hardcoded placeholder keys are
gone and cannot be reintroduced, vault and keychain hold no plaintext map at all, and workload
identity uses HMAC-SHA256 with a redacting, zeroizing seed newtype.

But `ManagedBackend` has no persistence and no KMS — the KEK lives in process memory beside the
ciphertext — and there is still no daemon-facing path to `provision()`. **`environment` remains
the only backend that returns material in this release.** The others refuse honestly with
`secrets.backend-not-configured` rather than silently answering "not found".

### `cached_tokens` and `reasoning_tokens` are still always `NULL`

The columns exist, the aggregation counts and sums them, and nothing ever writes them: the
runtime's `ModelUsage` carries `prompt_tokens`, `completion_tokens` and `cost_micros` and no
such fields. They are honest placeholders, not measurements, and they are rendered as explicitly
unavailable rather than as zero.

The wider rule still holds everywhere it is claimed: unmeasured values stay `NULL`. A run with
no measured cost keeps `cost_micros == None` and is charged nothing, never a fabricated zero the
cost budget could treat as a satisfying spend; an absent latency is never treated as 0 ms.

### A sandbox profile with a non-empty network allowlist is still refused outright

Deliberate fail-closed behaviour, and the bubblewrap generator's doc comment now says so
correctly ("the executor rejects any non-empty list before using this generator"). The Seatbelt
generator still carries a `if !profile.network_allowlist.is_empty()` branch and a comment
describing coarsened outbound-IP permission; that branch is dead, because the profile is refused
before the generator runs. Cosmetic, but do not read it as a capability.

## Migrations

**None.** No new root SQLite migration and no new PostgreSQL migration. The highest root
migration is `0049`, and root migrations remain append-only and checksum-gated.

The five PostgreSQL migrations `0006`–`0010` still create tables that no code in the repository
reads or writes. They are forward-looking schema, not a working subsystem, and they are applied
at startup by a service that is not in the release.

## Upgrading

```sh
codypendent update v0.11.0
```

or

```sh
curl -fsSL https://raw.githubusercontent.com/CodeHalwell/codypendent/main/install.sh | bash -s -- v0.11.0
```

`install.sh` requires the GitHub CLI (`gh`) on `PATH`. The companion surfaces come from the same
release:

```sh
codypendent install desktop          # Apple Silicon macOS / x86_64 Linux only
codypendent install vscode           # or: --in cursor
```

Local-first operation is unchanged and remains the only supported mode: the daemon starts and
runs with no control-plane configuration and no network. Nothing in this release introduces a
hosted dependency or any automatic sharing of source, transcripts, artifacts, memories or
credentials.

Two new local behaviours are worth knowing about before you upgrade:

* **The automation tick loop starts by default** and will fire any enabled binding whose
  `next_fire_at` has passed. If rows exist in `automation_bindings` from an earlier release, they
  were inert then and are live now. `missed_run` and the 120-second grace window decide what
  happens to a backlog.
* **The inbound webhook listener still does not start** unless `<data_dir>/webhooks.toml` sets
  `enabled = true`, and it still does not dispatch to automation unless that file *also* sets
  `automation_dispatch = true`. Both default to off.

If a previous release built a code graph rooted at your home directory, the new root check will
refuse to rescan it and the budgets will keep any future scan bounded. `codypendent graph build`
reports what the fold saw, including the per-extension breakdown of what produced nothing, so an
empty or truncated graph explains itself.

## For contributors

The lesson v0.10.0 ended on was "grep for the symbol, then check that something calls it." This
wave applied it and it worked — the automation tables, `analytics_budgets`, `automation_endpoints`
and the budget evaluator all had exactly that shape and all now have production callers.

The refinement v0.11.0 adds is that **a feature has two ends, and finding a caller for one of
them is not finishing it.** `ManageAutomationBinding` is the case study: the daemon end is
immaculate — role floor, real `named_resources()`, guard-test entry, integration coverage — and
the feature is still unusable because nothing on the client end constructs the command. The
grep that would have caught it is the same grep, run from the other direction: for every command
in the protocol, name the production file that builds it.

`role_permits` still ends in `_ => false`, and
`every_client_issued_command_has_a_decided_role_floor` is still the only thing standing between a
new client-issued command and a feature that is role-denied for every client while all of its
unit tests pass. An empty `named_resources()` makes the ownership gate pass **vacuously** — that
is how `ListSessions` once leaked across users. A test that calls a handler directly bypasses
both gates and proves nothing about reachability: if your proving test would still pass after
reverting your fix, it is not a proving test.
